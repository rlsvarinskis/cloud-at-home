# services/agentd

`services/agentd` runs LLM agents on top of vmd's virtual machines. A user creates an agent bound to one VM and
queues tasks for it. Worker goroutines claim queued tasks under a database lease, ask a language model (Ollama) what
to do next, and let it run commands through a single `bash` tool inside the VM. Every message and command is stored,
so another worker can resume a task whose owner died.

Module path: `github.com/rlsvarinskis/cloud-at-home/services/agentd`.

## Packages

- `cmd/agentd`: the server binary. It serves the agent API and runs the task workers. Without `-postgres-dsn` it uses
  the in-memory store and logs that state is lost on restart.
- `domain`: the internal model (Agent, Task, Step, Message) and state enums (`AgentActive`, `TaskQueued`, ...).
- `service`: the public API (`AgentServer`, `TaskServer`, `ModelServer`) and the HTTP surface (`NewHandler(Deps)`).
- `runner`: the worker loop. `New(Config)` returns a `Runner` with `Hooks`. It holds the lease, runs the model turns
  and the tools, and `Clean` sanitizes text before it is stored or sent to the model.
- `runner/toolcall`: repairs and normalises the tool calls models make (`LenientJSON`, `Normalize`, `ParseHarmony`).
- `runner/applypatch`: the `apply_patch` format (OpenAI's), as a pure parser and applier over a small `FS` interface.
  `runner/vmfs.go` implements that `FS` on an agent's VM.
- `llm`: the `Client` interface for model backends, `NewOllama(url)`, and `Fake` (a scripted backend with `Say`,
  `CallTool`, parse errors, cut-off replies and endless streams) for tests.
- `vmclient`: the `VM` interface, the only way agentd touches VMs. `New` wraps vmd's public Connect API.
- `store`: the `Store` interface, and `Memory`. `store/postgres` implements it on PostgreSQL (`Migrate`, `New`).
  `store/storetest` is the conformance suite.
- `metrics`: Prometheus series for the runner (`New(registerer)`).
- `llm/mock`, `store/mock`, `vmclient/mock`: gomock mocks generated by `make mocks`.

## Behaviour

A task runs a loop: the model replies, its tool calls run in the VM, and the results go back to the model. These
guards keep a run from going on forever or from ending on a bad tool call. The reasons are in
[ADR 4](../../docs/adr/0004-agent-loop-guards.md).

**Tool calls.** The model is always offered `bash`. Models named `gpt-oss*` are also offered `apply_patch`, which
edits files in the VM relative to the agent's working directory (the same directory `bash` starts in). Calls are
normalised before they run: tool names such as `shell`, `exec` or `functions.bash` become `bash`; `python` runs its
code through a `python3` heredoc; argv lists such as `["bash","-lc",X]` become `X`; a `workdir` becomes a `cd`.
A call Ollama cannot parse is repaired when its arguments are a JSON object (missing closing brackets, raw newlines
in strings). If it cannot be repaired, the model is told why and asked to re-emit it. A harmony-style call
(`to=functions.bash ...`) leaked into the text is run as a call. Four unusable calls in a row end the task in state
`error`; a good call resets the count.

**Token cap.** Each reply is limited to `max_call_tokens` (default 32768; 0 means no cap). A reply that hits the cap
is discarded and the model is asked to wrap up or make a shorter call.

**Repetition.** While a reply streams, the last 500 characters are checked every 16 pieces. A phrase of 24
characters with at least 8 letters or digits that occurs at least 8 times in that window means the output is
repeating itself. The call is aborted (Ollama stops generating), the reply is discarded and the model is asked to
wrap up.

**Cut replies.** After more than two cut replies (repetition or token cap) the task ends `gave_up` with `reason`
`repetition` or `token_limit`. If a `check_command` is set, it runs first: a pass ends the task as `succeeded`, a
failure as `gave_up`.

**Time limit.** `max_minutes` (default 0, no limit) counts from the start of the task. When it runs out the task
ends `cancelled` with `reason` `timeout`, and a running command is killed.

**Check after each batch.** With a `check_command` and `check_each_step` (default true), the check runs after each
batch of commands that ran. When it exits 0 the task ends `succeeded` at once, with `verdict_source` `check` and
`reason` `check passed`.

**Verdicts.** With a `check_command`, the check decides the state, and `verdict_source` is `check`. Without one, the
model's `VERDICT:` line decides (`verdict_source` `model`), and a claimed success is `succeeded_unverified`, never
`succeeded`. A task never ends with an empty result: an empty one gets a note, and a success with no result ends in
`error`.

**Progress.** Each model call is recorded (`calls`: index, seconds, tokens, end, partial, note), and the counters are
kept on the task: `model_calls`, `partial_calls`, `prompt_tokens`, `completion_tokens`, `first_token_seconds`,
`first_command_seconds`. An aborted call counts one generated token per streamed chunk and is marked `partial`. While a
call streams, `live_answer` and `live_reasoning` are written about once a second; they are cleared when the call
ends and are never part of the result.

**Defaults and limits.**

| Setting | Default | Where |
| --- | --- | --- |
| `max_steps` (commands per task) | 40, at most 200 | task |
| `max_minutes` | 0 (no limit) | task |
| `max_call_tokens` | 32768 (0 = no cap) | task |
| `check_each_step` | true | task |
| consecutive unusable tool calls before `error` | more than 3 | constant `maxParseFails` |
| cut replies before `gave_up` | more than 2 | constant `maxCuts` |
| repetition window / phrase / repeats | 500 characters / 24 characters with 8 letters or digits / 8 | constants in `runner/loop.go` |
| live text | about 1 update per second; 600 characters of answer, 300 of reasoning | constants in `runner/loop.go` |
| GPU memory budget for `fits_vram` | 16 GiB, less 0.5 GiB headroom | flag `-vram-gib` |

`fits_vram` compares a model's size on disk with the budget. It is a rough, weights-only check: the KV cache and the
runtime are not counted, so a model that is "fitting" may still run partly on the CPU.

## Public entry points

- `service.NewHandler(Deps)`: the Connect handlers for AgentService, TaskService and ModelService.
- `runner.New(Config)` and `runner.Runner` (its workers run until the context ends).
- `llm.NewOllama(baseURL)`, `llm.Fake` for tests. `Client.Chat` takes `ChatOptions` (the token cap) and reports a
  malformed tool call as `*llm.ToolParseError`.
- `toolcall.LenientJSON`, `toolcall.Normalize`, `toolcall.ParseHarmony`, `applypatch.Apply`.
- `vmclient.New(httpClient, baseURL, tokens)`.
- `store.NewMemory()`, `postgres.New(pool)` and `postgres.Migrate(ctx, pool)`.

## Dependencies

- Depends on `api` (the agentd API and the vmd API it calls), `libs/common` (`errs`, `ids`, `pg`), `libs/authz`
  (RBAC and service tokens) and `libs/server` (`daemon`, `obs`).
- Must NOT depend on `libs/qemu` or `services/vmd`. agentd uses vmd only through its public API, as a service
  principal, and shares no database with it. This is checked by `scripts/check-boundaries.sh`.
- External: `connectrpc.com/connect`, `pgx/v5`, `prometheus/client_golang`, `go.uber.org/mock` (mocks).

## Build and test

```
cd services/agentd && go build ./...
cd services/agentd && go test -race ./...
```

Tests run the store conformance suite against memory and Postgres, and the service and runner tests use the fake
LLM and the mock VM client. Postgres tests start a database through `libs/common/pg/pgtest` unless
`ATTIC_TEST_POSTGRES` points at one. Runner lease tests use short real-time TTLs, which can be sensitive to
load.

## Notes and limitations

- The only model backend is Ollama. The `llm.Client` interface exists so that others can be added.
- Authorization is checked per call with `RequireResource` / `RequireAnyProject` in the service handlers.
- Task queue depth is not exported as a metric, because the store has no cluster-wide count.
- The runner's correctness depends on the lease: a worker that lost its lease must not write a final state. Lease
  timing is in real time, so tests that rely on it can be flaky under load.
- The Postgres store is the only durable one. The memory store loses agents and tasks on restart.
- The loop guard counters (consecutive unusable tool calls, cut replies) are per worker run, not stored; see
  [ADR 4](../../docs/adr/0004-agent-loop-guards.md).
- `Clean` removes NUL bytes and replaces invalid UTF-8, because Postgres `TEXT` cannot hold NUL. Other binary
  output from commands is not treated specially here.
- The `e2e` module drives agentd and vmd together over their real APIs.
